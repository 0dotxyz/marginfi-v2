# Variable Borrow Premium PR Review

Reviewed for fitness for purpose, security, and code quality against the attached feature specification. The findings below use VS Code file links so they open at the relevant line in the editor.

## 1. P1 — Direct liquidation can silently discard accrued premium

Direct liquidation repays the liquidatee's liability through [`BankAccountWrapper::repay`](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/instructions/marginfi_account/liquidate.rs:443:1). That path first materializes premium but, once the liability shares fall below the empty-balance threshold, it [clears `premium_outstanding`](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/state/marginfi_account.rs:2461:1) without moving it to `bank.collected_premium_outstanding`.

This differs from a normal repayment: the handler [claims the premium and then settles it before reducing principal](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/instructions/marginfi_account/repay.rs:90:1). `settle_premium` is explicitly the operation that moves a receivable into the bank's collected-premium counter when the corresponding tokens reach the liquidity vault ([implementation contract](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/state/marginfi_account.rs:2066:1)).

Consequently, a liquidation that fully (or nearly fully) clears a liability can materialize its premium and then erase it. The protocol has neither collected the premium into its accounting counter nor made an explicit, auditable write-off decision. This contradicts the expected liquidation outcome in [Story 5](vscode://file//home/fish/Downloads/0d291e24-fbe4-4df0-9413-fb321c005697_ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1/ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1-Part-1/Private%20%26%20Shared/Variable%20Borrow%20Premium%2030cff20a24da802cb776f634bf72dac8.md:435:1), which says liquidation repays debt including premium.

The liquidation path needs an explicit economic treatment for the premium: settle it from payment tokens when they are available, or deliberately write it off with distinct accounting/event semantics when it is not. It must not fall through the generic empty-balance cleanup.

## 2. P1 — Disabling premium retroactively forgives outstanding receivables

The premium configuration instruction disables the feature by [clearing `PREMIUM_ACTIVE`](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/instructions/marginfi_group/config_bank_premium.rs:30:1). It does not first preserve or settle premium that accrued while the bank was active.

After that, every path that claims premium [zeros `premium_outstanding` and returns](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/state/marginfi_account.rs:2040:1). Health-driven snapshot refresh has the same effect: an inactive liability [clears the receivable and its snapshot](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/state/premium.rs:240:1). The generic balance-mutation paths also independently clear it when the bank is inactive ([one such path](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/state/marginfi_account.rs:2374:1)).

An administrator can therefore turn the feature off and thereby erase already-accrued, unpaid premium on every affected borrower at their next interaction or health refresh. Turning off premium should stop *future* accrual; it should not make a previously earned receivable vanish. This is a material accounting and governance risk, particularly because there is no user action that can guarantee settlement before the administrator changes the flag.

Preserve existing `premium_outstanding` across deactivation and stop only new accrual (for example by setting future snapshots to zero after first claiming at the old rate). If write-offs are intended, they need explicit authorization, an event, and a reason rather than being an incidental side effect of a configuration toggle.

## 3. P2 — Deposit and repay do not refresh all premium snapshots, so Story 3 is not met

The specification says a rate snapshot is recomputed on *any* account action, including deposit and repay ([Story 1 notes](vscode://file//home/fish/Downloads/0d291e24-fbe4-4df0-9413-fb321c005697_ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1/ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1-Part-1/Private%20%26%20Shared/Variable%20Borrow%20Premium%2030cff20a24da802cb776f634bf72dac8.md:123:1)). More specifically, Story 3 requires a collateral deposit to recompute every liability's snapshot ([required internal action](vscode://file//home/fish/Downloads/0d291e24-fbe4-4df0-9413-fb321c005697_ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1/ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1-Part-1/Private%20%26%20Shared/Variable%20Borrow%20Premium%2030cff20a24da802cb776f634bf72dac8.md:200:1)).

The current deposit handler mutates only the selected balance via [`bank_account.deposit`](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/instructions/marginfi_account/deposit.rs:90:1) and performs no account-wide premium snapshot pass. The repayment handler similarly works only with its selected bank account ([selection and mutation](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/instructions/marginfi_account/repay.rs:86:1)). The account type documents this intentional limitation: snapshots are refreshed by oracle-carrying instructions, but [not by deposit or repay](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/type-crate/src/types/user_account.rs:293:1).

Therefore, depositing higher-quality collateral does not immediately lower the premium snapshot on an existing liability; repaying does not refresh the remaining liabilities either. The new rate is deferred until some later oracle-carrying instruction or `pulse_health`. That is not the behavior described in Story 3 and can overcharge or undercharge borrowers for an unbounded time if their next transaction is not an oracle-carrying one.

To satisfy the user stories, deposit and repay need an account-wide claim-and-snapshot refresh with the required bank/oracle accounts. If those account requirements are too expensive, the public contract and product flow must explicitly require a separate refresh instruction as part of the same user action; the implementation currently does neither.

## 4. P2 — Partial repayment settles premium first, contrary to Story 6

The specification says a partial `repay(amount)` reduces liability shares only, keeps premium accruing on the remaining debt, and settles premium on `repay_all` ([Story 6 note](vscode://file//home/fish/Downloads/0d291e24-fbe4-4df0-9413-fb321c005697_ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1/ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1-Part-1/Private%20%26%20Shared/Variable%20Borrow%20Premium%2030cff20a24da802cb776f634bf72dac8.md:515:1)). It separately identifies that choice as the recommended policy ([section 4.3](vscode://file//home/fish/Downloads/0d291e24-fbe4-4df0-9413-fb321c005697_ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1/ExportBlock-ae90a3c5-70c3-4f2b-8868-5ea29d5875b1-Part-1/Private%20%26%20Shared/Variable%20Borrow%20Premium%2030cff20a24da802cb776f634bf72dac8.md:785:1)).

Instead, a partial repayment first [claims and settles premium](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/instructions/marginfi_account/repay.rs:90:1), subtracts it from the caller's amount, and only [applies the remainder to principal](vscode://file//home/fish/mrgn/marginfi-v2/marginfi-v2/programs/marginfi/src/instructions/marginfi_account/repay.rs:98:1). A borrower who repays 100 units therefore reduces base debt by less than 100 units whenever there is accumulated premium, and the premium fund is realized earlier than the specified flow permits.

This is not inherently unsafe if it is a deliberate product decision, but it is a clear user-story mismatch with balance, health, and fee consequences. Either change the code so partial repayments reduce principal only and reserve settlement for `repay_all`, or revise the specification and user-facing repayment quotes to make the fee-first behavior explicit.
